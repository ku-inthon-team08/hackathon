# 고요하길 BE: 서울 전체 확장 (중단 기록, 2026-10-31)

시간이 오래 걸리고 다른 팀과 주제가 겹쳐서, 프로젝트를 "외국인을 위한 물가 서비스"로 전환하며 이 작업은 중단했다.
작업은 `BE-seoul` 브랜치에 있고 main에는 합치지 않았다.

## 측정값 (anon 키로, 교체 직후 부하가 있는 상태)

- 교체 시간: 1차는 앱 점검이 10분 넘게 끝나지 않아 취소·롤백, 2차 약 8분 성공
- `quiet_routes` 약 1~1.4km(첫 호출 / 두 번째): 강남 1.57 / 0.79초, 종로 1.19 / 0.77초, 노원 1.64 / 0.93초, 강서 2.60 / 1.07초, 마포 1.00 / 1.31초
- 실패: 장거리 경로(잠실→강남 약 7km), `map_layers`(서울 전체 화면 · 강남 한 화면), `nearby_shelters`(마포)가 8초 제한 초과
- 보안 점검(advisors): ERROR 1(`latest_congestion` 뷰가 SECURITY DEFINER, 원래 있던 것), WARN 12(앱 RPC 6개를 anon·authenticated가 실행, 의도한 것), INFO 17(정책 없는 내부 테이블, 의도한 것)

## 남은 문제 (이어서 할 경우)

1. FE가 화면 범위가 아니라 `MAP_BOUNDS` 전체를 타일 24개로 부르고, 실패하면(옛 코드) 쪼개 다시 부른다. 서울 데이터에서 DB CPU가 포화된다 → 화면 범위만 부르게 바꿔야 한다.
2. `place_exposure()`를 함수로 부르면 한 곳에 7.4초, 같은 쿼리를 `prepare`로 돌리면 0.16초. 원인 미확인(보안 정의자 SQL 함수의 계획 문제로 추정).
3. 장거리 경로는 탐색 사각형이 커져 8초를 넘는다 → 거리 상한이나 탐색 범위 제한이 필요하다.
4. 고정 데이터를 서울 전체로 적재하지 못했다: 서비스 키 · `SEOUL_API_KEY`가 이 환경에 없고 `openapi.seoul.go.kr:8088`이 막혀 있었다. 필요한 파일(서울 열린데이터광장): OA-21285 `서울시 주요 121장소 영역.zip`, OA-22833 S-DoT 환경정보 주간 CSV + 설치 위치 xlsx, OA-22832 S-DoT 유동인구 주간 CSV + 설치 위치 xlsx. 쉼터는 OpenAPI(도서관 · 작은도서관 · 무더위쉼터 · 공원).
5. `sensor_obs` 보관 기간: 서울 센서를 넣으면 하루 수 MB씩 쌓인다.
6. 마포로 되돌리려면 `scripts/road_network/import_road_network.sql`을 마포 CSV(커밋 `9485f8f`의 `data/road_network/mapo_road_*.csv`)로 돌린다.

## 오래 걸린 것과 교훈

- **클라우드 세션에 비밀값이 없었다**(서비스 키, DB 비밀번호, 서울 API 키). 시작할 때 환경변수부터 확인하고, 없으면 바로 말할 것. 이번에는 CSV를 공개 레포에 올리고 DB가 `pg_net`으로 받아 SQL로 넣었다.
- **네트워크 정책**: `overpass-api.de`, `download.geofabrik.de`, `openapi.seoul.go.kr:8088`이 막혀 있었다. `download.bbbike.org`, `data.seoul.go.kr`, PyPI·npm, GitHub raw는 됐다.
- **Supabase 무료 플랜이 작다**: 공유 CPU라 25만 행 GiST 인덱스를 한 줄씩 갱신하면 9분 걸렸다. 인덱스는 다 넣은 뒤 한 번에 만든다. 큰 작업 뒤에는 자동 VACUUM(10분 이상)과 앱 요청이 겹쳐 모든 요청이 8초 제한에 걸리고, pg_cron도 "job startup timeout"으로 실패했다.
- **REST(PostgREST)**: 한 번에 1000행까지만 돌려주고 요청마다 8초 제한이 있다. 대량 적재는 REST로 하지 말 것.
- **MCP `execute_sql`은 60초 제한**이 있고 시간이 넘어도 서버에서는 계속 돈다. 긴 작업은 pg_cron 일회성 작업으로 돌린다.
- **pg_cron 함정**: 여러 문장 명령은 첫 문장(`set`)이 끝나면 'succeeded'로 기록한다. 진짜 끝났는지는 `pg_stat_activity`로 본다. 작업 중에 테이블 크기를 재는 쿼리는 잠금에 막힌다.
- **롤백해도 남는 것**: 트랜잭션 안의 ANALYZE가 바꾼 행 수 통계(`pg_class.reltuples`)는 롤백돼도 남아서, 실패 뒤 `analyze`를 다시 해야 했다. 롤백된 행은 죽은 행으로 남아 용량을 차지한다(255MB → `VACUUM FULL` 후 62MB).
- **뷰 설계**: 25만 행 테이블 여러 개를 조인하는 뷰를 RPC가 매번 읽으면 범위 안 몇천 행만 필요해도 전체를 조인한다. 바뀌지 않는 값은 한 테이블에 미리 모아 두면 기본키로 찾아 붙인다(48ms).
- **공유 DB 동시 작업**: 팀원이 같은 시간에 같은 테이블에 업로드를 시도해 충돌할 뻔했다. 큰 작업 전에 팀에 알린다.
- **FE 로딩 방식이 DB 부하를 결정한다**: 데이터를 넓히기 전에 FE가 화면 범위만 부르는지 먼저 확인한다.
